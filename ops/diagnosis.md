# Storage Startup Diagnosis

## Observed fault

An isolated exercise set DB_PATH beneath a regular file instead of a directory. Application startup failed with FileExistsError when the repository attempted to create the parent directory. This reproduces a storage-configuration failure, not a production incident.

The AI-assisted diagnosis was that a valid, writable directory must contain the SQLite file. Using a new directory allowed startup and a 201 save response; reopening the application returned the same saved record with status 200.

[Raw observed output](reports/storage-diagnosis.json) was generated by [the diagnostic script](diagnose_storage.py). All paths and records used by the exercise were temporary. No real database was read, deleted, or repaired.

## Reproduce safely

With project dependencies installed, run from the repository root:

```bash
python ops/diagnose_storage.py
```

The script creates its own temporary directory, injects the failure, verifies recovery and persistence, then removes only its temporary data. It does not accept a production database path.

## Operational checklist

If startup fails, inspect the exception type and DB_PATH. Confirm that its parent is a directory and is writable by the application user. Check available disk space and volume mounting. Preserve existing files before investigating; do not erase a database as a shortcut.

For Docker, inspect `docker compose ps` and `docker compose logs --tail=100 app`. Confirm the named volume is mounted at `/data` and belongs to a user the non-root container process can access. The Docker execution of these checks remains unverified because the local engine was unavailable.

No cloud service or open-source AI operations agent was used in this exercise. If the course requires that specific integration, its output is still needed.
